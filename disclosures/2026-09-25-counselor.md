# Counselor

## Iterative Process Control Extension

**Type:** Technical Architecture Extension / Prior-Art Publication
**Extends:** Authorization Agent v1.0 and subsequent architectural extensions
**Status:** Public technical disclosure

---

## 1. Purpose

The **Counselor** is the iterative control component of the Authorization Agent architecture.

Its purpose is to determine whether the current process should:

* begin another iteration,
* terminate,
* or request a controlled break from the Core.

The Counselor therefore provides the architectural equivalent of an iterative:

```text
FOR / NEXT
```

control structure.

The Counselor does not define the concrete instruction executed within an iteration and does not authorize that instruction.

The fundamental separation is:

```text
Counselor
    → submits a process request

Core
    → returns a deterministic process response

Planner
    → defines the instruction for an opened iteration

Decisioner
    → evaluates authorization

Core
    → enforces authorization and produces the effect
```

---

# 2. Process Requests and Core Responses

The Counselor–Core protocol explicitly separates requests from responses.

A **Process Request** originates from the Counselor:

```text
COUNSELOR → CORE
```

A **Core Response** originates from the Core:

```text
CORE → COUNSELOR
```

These are distinct protocol message classes.

### Process Requests

The Counselor may submit:

```text
NEXT_ITERATION_REQUEST
BREAK_REQUEST
GOAL_STATUS_REQUEST
```

### Core Responses

The Core may return corresponding responses such as:

```text
ITERATION_OPEN
BREAK_ACCEPTED
BREAK_REJECTED
GOAL_STATUS_RESPONSE
CONTINUATION_DENIED
ITERATION_LIMIT_REACHED
PROCESS_HALTED
```

A Core Response is never generated by the Counselor.

A Process Request is never generated by the Core.

---

# 3. NEXT Iteration Request

When the Counselor determines that another iteration may be required, it submits:

```text
NEXT_ITERATION_REQUEST
```

The request means:

> **The Counselor requests that the Core evaluate whether another iteration may be opened.**

It does not mean:

```text
ALLOW
```

and it does not itself open the iteration.

The flow is:

```text
Counselor
    │
    │ NEXT_ITERATION_REQUEST
    ▼
Core
    │
    │ Core evaluation
    ▼
Core Response
```

If continuation is permitted:

```text
CORE RESPONSE:
    ITERATION_OPEN
```

If continuation is not permitted:

```text
CORE RESPONSE:
    CONTINUATION_DENIED
```

or, where applicable:

```text
CORE RESPONSE:
    ITERATION_LIMIT_REACHED
```

---

# 4. Iteration Opening

Only the Core can establish the process state:

```text
ITERATION_OPEN
```

The Counselor cannot declare an iteration open merely by sending:

```text
NEXT_ITERATION_REQUEST
```

The correct sequence is:

```text
Counselor
    │
    │ NEXT_ITERATION_REQUEST
    ▼
Core
    │
    │
    ├── ITERATION_OPEN
    │
    ├── CONTINUATION_DENIED
    │
    └── ITERATION_LIMIT_REACHED
```

Only after:

```text
CORE RESPONSE = ITERATION_OPEN
```

does the Planner receive the new iteration.

---

# 5. Planner Instruction

After the Core has opened an iteration:

```text
Core
    │
    │ ITERATION_OPEN
    ▼
Planner
```

The Planner then produces:

```text
ITERATION_INSTRUCTION
```

This is a separate protocol message from the Counselor's process request.

The flow becomes:

```text
Counselor
    │
    │ NEXT_ITERATION_REQUEST
    ▼
Core
    │
    │ ITERATION_OPEN
    ▼
Planner
    │
    │ ITERATION_INSTRUCTION
    ▼
Decisioner
    │
    │ authorization decision
    ▼
Core
    │
    │ deterministic enforcement
    ▼
EFFECT
```

Thus the Counselor does not create the Planner instruction, and the Planner does not create the iteration itself.

---

# 6. BREAK Request

The Counselor may request a controlled break:

```text
BREAK_REQUEST
```

This is a Process Request.

The Core returns a separate Core Response.

```text
Counselor
    │
    │ BREAK_REQUEST
    ▼
Core
    │
    ├── BREAK_ACCEPTED
    │
    ├── BREAK_REJECTED
    │
    └── PROCESS_HALTED
```

The Counselor cannot directly place the Core into a break or halt state.

It can only request the corresponding transition.

The Core determines and enforces the resulting process state.

---

# 7. Goal Status Request

The Counselor may request information concerning the current state of the Objective:

```text
GOAL_STATUS_REQUEST
```

This is a Process Request.

The Core returns:

```text
GOAL_STATUS_RESPONSE
```

This is a Core Response.

The protocol therefore explicitly separates the two:

```text
Counselor
    │
    │ GOAL_STATUS_REQUEST
    ▼
Core
    │
    │ GOAL_STATUS_RESPONSE
    ▼
Counselor
```

For example:

```text
GOAL_STATUS_RESPONSE:
    ACHIEVED
```

or:

```text
GOAL_STATUS_RESPONSE:
    NOT_ACHIEVED
```

or another state defined by the Core protocol.

---

# 8. Planner Does Not Initiate Goal Status Requests

The Planner may produce information relevant to goal assessment.

For example:

```text
ITERATION_RESULT
RESULT_INFORMATION
STATE_OBSERVATION
```

However, the Planner does not determine whether a goal-status query should be made.

The decision to submit:

```text
GOAL_STATUS_REQUEST
```

belongs to the Counselor.

Thus:

```text
Planner
    → supplies relevant iteration information

Counselor
    → requests goal-status evaluation

Core
    → returns goal-status information
```

This prevents the Planner from controlling the iteration mechanism through its own interpretation of success.

---

# 9. Goal Status Does Not Determine Continuation

A `GOAL_STATUS_RESPONSE` is information returned by the Core.

It does not itself constitute a `NEXT_ITERATION_REQUEST`.

For example:

```text
Core → Counselor

GOAL_STATUS_RESPONSE:
    NOT_ACHIEVED
```

does not automatically produce:

```text
NEXT_ITERATION
```

Instead:

```text
GOAL_STATUS_RESPONSE
        │
        ▼
Counselor
        │
        │ process evaluation
        ▼
NEXT_ITERATION_REQUEST
```

The Counselor therefore remains responsible for deciding whether another iteration should be requested.

---

# 10. Maximum Iteration Count

The Counselor evaluates whether another iteration is useful.

It does **not** determine whether another iteration is permitted under the Core's hard constraints.

For example:

```text
Counselor
    │
    │ NEXT_ITERATION_REQUEST
    ▼
Core
    │
    │ iteration limit reached
    ▼
ITERATION_LIMIT_REACHED
```

The Counselor cannot convert:

```text
ITERATION_LIMIT_REACHED
```

into:

```text
ITERATION_OPEN
```

The iteration limit is a Core-controlled constraint.

Therefore:

```text
Counselor
    → Is another iteration useful?

Core
    → Is another iteration permitted?
```

---

# 11. Counselor Optimization Objective

The Counselor has the process-level optimization objective:

> **Complete the authorized Objective successfully in as few iterations as reasonably possible.**

The Counselor therefore evaluates:

* progress toward the Objective,
* results of previous iterations,
* whether additional work is useful,
* whether the Objective has been achieved,
* and whether another iteration is justified.

It does not optimize by weakening authorization, safety, or Core constraints.

Conceptually:

```text
minimize iterations
        subject to
        ├── authorization constraints
        ├── Core constraints
        ├── information constraints
        ├── safety constraints
        └── iteration limits
```

---

# 12. Process Request Does Not Equal Authorization

A Process Request from the Counselor is not an authorization decision.

For example:

```text
NEXT_ITERATION_REQUEST
```

does not mean:

```text
ALLOW
```

and:

```text
BREAK_REQUEST
```

does not mean:

```text
HALT
```

The Core must produce the corresponding deterministic response.

Likewise:

```text
GOAL_STATUS_REQUEST
```

does not mean:

```text
GOAL_STATUS = ACHIEVED
```

The Core provides the actual response.

---

# 13. Complete Iteration Protocol

A complete iteration therefore follows two distinct protocol layers.

### Process-control layer

```text
Counselor
    │
    │ NEXT_ITERATION_REQUEST
    ▼
Core
    │
    │ ITERATION_OPEN
    ▼
Planner
```

### Authorization / execution layer

```text
Planner
    │
    │ ITERATION_INSTRUCTION
    ▼
Decisioner
    │
    │ ALLOW / DENY / CLARIFY
    ▼
Core
    │
    │ deterministic enforcement
    ▼
EFFECT
```

After the effect:

```text
EFFECT / RESULT
        │
        ▼
Counselor
        │
        ├── GOAL_STATUS_REQUEST
        │
        ├── NEXT_ITERATION_REQUEST
        │
        └── BREAK_REQUEST
```

Each Counselor request again requires a separate Core response.

---

# 14. Protocol Directionality

The protocol can therefore be stated formally:

```text
PROCESS REQUESTS:

Counselor → Core
```

```text
CORE RESPONSES:

Core → Counselor
```

```text
ITERATION INSTRUCTIONS:

Planner → Decisioner / Core
```

```text
AUTHORIZATION DECISIONS:

Decisioner → Core
```

```text
EXECUTION EFFECTS:

Core → External System / Effect Target
```

The direction of each protocol message is therefore explicit.

---

# 15. Fundamental Separation

The architecture can now be summarized as:

```text
                 COUNSELOR
                 FOR / NEXT
                     │
                     │ Process Request
                     ▼
                   CORE
                     │
                     │ Core Response
                     ▼
                  PLANNER
                     │
                     │ Iteration Instruction
                     ▼
                DECISIONER
                     │
                     │ Authorization Decision
                     ▼
                   CORE
                     │
                     │ Enforcement
                     ▼
                  EFFECT
                     │
                     ▼
                 COUNSELOR
```

The programming analogy is:

> **The Counselor is the iterative control structure. The Planner is the body of the iteration. The Decisioner evaluates authorization. The Core is the deterministic conditional and enforcement boundary.**

The key protocol rule is:

> **Every Process Request is a request. Every Core Response is a response. Neither side may impersonate the other by encoding a response as a request or a request as a response.**

This makes the Counselor–Core interface an explicit state-transition protocol rather than an informal conversation.
